# Inspect Output

After compiling a CRADLE scenario, CradleXC produces structured output that you can inspect before generating any backend-specific files.

For the Hello World example, compilation produces:

```text
HelloWorld.yml
```

You can also inspect CradleXC's intermediate representation with `cxc dump-ir`.

This page explains how these outputs fit into the CRADLE workflow.

## Output workflow

The basic inspection flow is:

<div className="architecture-flow">

  <div>CRADLE source</div>

  <span>↓</span>

  <div>Validate</div>

  <span>↓</span>

  <div>Compile</div>

  <span>↓</span>

  <div>Compiled YAML</div>

  <span>↓</span>

  <div>Inspect output</div>

</div>

Backend-specific generation happens separately after this stage.

## Compile the scenario

If you have not already compiled the scenario, run:

```bash
cxc compile \
  -i scenarios/HelloWorld.cradle \
  -o HelloWorld.yml
```

This creates:

```text
HelloWorld.yml
```

The YAML file contains the compiled representation produced by CradleXC from the source scenario.

:::note
The compiled YAML is CradleXC output. It is different from the target-specific files generated by a backend plugin.
:::

## Open the compiled YAML

You can inspect the generated file using any text editor.

From the terminal, you can also display it with:

```bash
cat HelloWorld.yml
```

For longer files, use a pager such as:

```bash
less HelloWorld.yml
```

The exact contents depend on the CRADLE scenario and the version of CradleXC used to compile it.

## What to inspect

When reviewing compiled output, check that the scenario structure reflects what you defined in the `.cradle` source.

For example, the Hello World scenario contains:

- the `HelloWorld` and `router` instances
- the `lan_0` network
- the `HelloWorld` object
- scenario metadata
- the `preEvent`, `mainEvent` and `postEvent` lifecycle phases
- events `1`, `2` and `3`

The compiled representation should reflect these parts of the source scenario.

## Compare source and compiled output

The source file describes the scenario using CRADLE syntax:

```text
HelloWorld.cradle
```

CradleXC processes that source into structured YAML:

```text
HelloWorld.yml
```

Conceptually:

<div className="architecture-flow">

  <div>HelloWorld.cradle</div>

  <span>↓</span>

  <div>CradleXC</div>

  <span>↓</span>

  <div>HelloWorld.yml</div>

</div>

The two files serve different purposes.

| File | Purpose |
| --- | --- |
| `HelloWorld.cradle` | Human-authored CRADLE source scenario. |
| `HelloWorld.yml` | Structured compiled representation produced by CradleXC. |

The `.cradle` file remains the source that you edit.

The generated YAML should normally be treated as compiler output rather than as the primary scenario definition.

## Inspect the intermediate representation

CradleXC can also display the intermediate representation created while processing a scenario.

Run:

```bash
cxc dump-ir -i scenarios/HelloWorld.cradle
```

This allows you to inspect how CradleXC interpreted the source before working with backend-specific output.

:::note
You do not need to use `cxc dump-ir` during every workflow. It is mainly useful for inspection, debugging and understanding how a scenario has been interpreted.
:::

## When to use `dump-ir`

`cxc dump-ir` is useful when:

- you want to inspect how CradleXC interpreted a scenario
- compiled output does not match what you expected
- you are diagnosing a scenario-processing problem
- you are developing or debugging backend integration
- you need more information than syntax validation provides

The command does not modify the scenario.

It also does not generate target-specific backend files.

## Validation, IR and compiled output

These commands serve different purposes:

| Command | Purpose |
| --- | --- |
| `cxc validate` | Checks whether the CRADLE syntax is valid. |
| `cxc dump-ir` | Displays CradleXC's intermediate representation of the scenario. |
| `cxc compile` | Writes the compiled scenario representation to YAML. |

A typical workflow is:

```bash
cxc validate -i scenarios/HelloWorld.cradle

cxc dump-ir -i scenarios/HelloWorld.cradle

cxc compile \
  -i scenarios/HelloWorld.cradle \
  -o HelloWorld.yml
```

`cxc dump-ir` is optional, so a normal workflow can also be:

```bash
cxc validate -i scenarios/HelloWorld.cradle

cxc compile \
  -i scenarios/HelloWorld.cradle \
  -o HelloWorld.yml
```

## Investigate unexpected output

If the compiled YAML does not reflect what you expected, start by validating the source again:

```bash
cxc validate -i scenarios/HelloWorld.cradle
```

Then inspect the intermediate representation:

```bash
cxc dump-ir -i scenarios/HelloWorld.cradle
```

Finally, regenerate the YAML:

```bash
cxc compile \
  -i scenarios/HelloWorld.cradle \
  -o HelloWorld.yml
```

This helps separate problems in the source scenario from problems encountered later during backend-specific generation.

For additional guidance, see [Troubleshooting](../guides/troubleshooting).

## Compiled output and backend output

Compiled YAML and backend-generated files are separate outputs.

The workflow is:

<div className="architecture-flow">

  <div>CRADLE source</div>

  <span>↓</span>

  <div>CradleXC</div>

  <span>↓</span>

  <div>Compiled representation</div>

  <span>↓</span>

  <div>Backend plugin</div>

  <span>↓</span>

  <div>Target-specific files</div>

</div>

`cxc compile` generates the compiled representation.

A backend plugin generates files for a particular target.

For example:

```bash
cxc emit \
  -i scenarios/HelloWorld.cradle \
  --target <plugin_name> \
  -o /path/to/output
```

The type and structure of the generated files depend on the selected backend.

:::important
CradleXC does not automatically execute backend-generated target files. Use those files with the corresponding tools in your own testbed environment.
:::

## Do not edit generated output as your source

When changing a scenario, edit the original `.cradle` file:

```text
HelloWorld.cradle
```

Then validate and compile it again.

Avoid treating generated YAML or backend-specific files as replacements for the CRADLE source.

This preserves the `.cradle` scenario as the authoritative definition of the environment.

## Example project after compilation

After compiling the Hello World scenario, your files might look like:

```text
.
├── HelloWorld.yml
└── scenarios/
    └── HelloWorld.cradle
```

If you later generate backend-specific files, keep them in a separate output directory where possible.

For example:

```text
.
├── HelloWorld.yml
├── output/
│   └── ...
└── scenarios/
    └── HelloWorld.cradle
```

This makes it easier to distinguish authored source from generated files.
