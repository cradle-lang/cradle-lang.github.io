# Contribute a Cyber Range

The [Cyber Range Collection](/collection/) stores reusable specifications in
Git alongside the website. Its initial entries are the existing Workbench
examples. NCL and NTNU scenarios are welcome when their sources, attribution
and redistribution permissions are available.

Published entries are working, deployable scenarios. Hello World and the complex
SME example are the initial accepted samples. Contributors should provide complete specifications and document their runtime
dependencies. The library validates and compiles source; it does not certify
that a simulation can run without those dependencies or launch it on GitHub.

Follow the steps below from checkout through publication. The repository also
includes `library/README.md` for contributors reading the source locally.

## Prepare your checkout

Install Git, Node.js 20 or newer (CI uses 22), and npm. Fork the
[website repository](https://github.com/cradle-lang/cradle-lang.github.io)
if you do not have write access. Replace `YOUR-GITHUB-USERNAME` with your account;
contributors with write access can clone upstream instead:

```bash
git clone https://github.com/YOUR-GITHUB-USERNAME/cradle-lang.github.io.git
cd cradle-lang.github.io
git switch -c add-my-range
npm ci
```

For an existing checkout, begin from an up-to-date `main` with a clean working
tree and create your contribution branch. Run the remaining commands from the
repository root. A local compiler or testbed is not required to build the website.

## Add a scenario folder

```bash
npm run library:new -- scenario my-range
```

This creates `library/scenarios/my-range/` from the template. Write `index.md`
(or rename it to `index.mdx`), replace `scenario.cradle` with the working
specification and put supporting images, scripts and configurations in the same
folder. Use relative Markdown links to include those assets in the rendered page.

To copy an existing scenario directory, including nested configurations,
artifacts and scripts, use:

```bash
npm run library:new -- scenario my-range --from "/path/to/my-range"
```

On Windows, use a quoted path such as `--from "C:\Users\bryan\Documents\my-range"`.
The first `my-range` is the destination folder name, without `.cradle`.
The source directory must contain a top-level `scenario.cradle`, or exactly one
top-level `.cradle` file, which is renamed in the copy. When there are multiple
specifications, name the main one `scenario.cradle` before importing.

An existing `index.md` or `index.mdx` is preserved; otherwise, a draft article is
created. Add `--mdx` to generate MDX or convert an imported Markdown article.
Review metadata and relative links, including any link to a renamed source.
Supporting files need article links to become usable downloads. Existing
destination entries are never overwritten, and the source remains unchanged.
The import skips `.git`, `node_modules` and `__pycache__` directories and rejects
symbolic links. Copied configs and artifacts still need the documented backend
setup; importing files does not install them on a testbed.

Fill in the front matter: `title`, `description`, original `source`, `category`,
non-empty `tags` and `requirements`. Include validation results, dependencies, attribution and a license in the article.
Document runtime tests and testbed/backend versions when available. Set `draft: false` when ready.
Docusaurus publishes the article at `/library/scenarios/my-range`; the library,
Workbench browser and GitHub workflows discover the folder ID automatically.

No catalog JSON, React imports, sidebar registration or workflow choices need
editing. The generated catalog is ignored by Git and rebuilt on preview/build.

## Scenario thumbnails

Every scenario has artwork even when you do not upload an image. Set the
optional `artwork` field in the article's YAML front matter:

| Value | Default artwork |
| --- | --- |
| `auto` (default) | Light blue for one network; dark blue for multiple networks |
| `network` | Light blue network illustration |
| `enterprise` | Dark blue enterprise illustration |
| `monitoring` | Green monitoring illustration |

### Add your own thumbnail

1. Place an image inside your scenario folder. For example:

   ```text
   library/scenarios/my-range/
     index.md
     scenario.cradle
     images/
       thumbnail.webp
   ```

2. Add the following fields inside the existing front matter in `index.md` or `index.mdx`. Keep the other required scenario fields:

   ```yaml
   artwork: monitoring
   thumbnail: ./images/thumbnail.webp
   thumbnailAlt: A diagram showing training hosts and the management network.
   ```

3. Preview the image on the scenario card, scenario detail page and in Workbench's library browser. The custom image takes priority over the built-in artwork. Important content should remain visible in every crop.
4. Commit the image with the article and specification, then follow the checks and pull request steps below. Images are published with the static website; no external image host or React edit is needed.

Use PNG, JPEG, WebP or GIF. A landscape image around **1200 × 675 pixels (16:9)**
is recommended; keep key content near the centre and optimize the file, ideally
below 500 KB. Use images you have permission to publish and record attribution
in the article. The alternative text must describe the image, not its filename.

Paths are relative to the scenario folder. External URLs and files outside that
folder are rejected. A missing file, unsupported format or missing `thumbnailAlt`
fails metadata generation with an actionable error. If a validly published image
fails to load in the browser, the selected built-in illustration is shown.
Remove `thumbnail` and `thumbnailAlt` to restore the default.

The thumbnail is used by the Library and Workbench browser. To also display it
inside the written guide, add a normal Markdown image:

```markdown
![Training hosts and management network](./images/thumbnail.webp)
```

Follow [Preview and publish](#preview-and-publish) to check the image and submit
the complete folder.

## Add configuration or heuristic documentation

```bash
npm run library:new -- configuration my-config
npm run library:new -- heuristic my-heuristic
```

Configurations and heuristics appear only when their own library articles are
published. References in a scenario do not create cards. Matching scenario
references supply usage counts and links for published entries.

Follow [Contribute a Configuration](./contribute-configuration) or
[Contribute a Heuristic](./contribute-heuristic) for metadata, implementation files,
examples and publication steps. Frameworks are derived from published heuristic
articles.

Start from the templates in `library/_templates/`, keep exactly one `index.md`
or `index.mdx` per folder, and set `draft: false` only after completing the entry.
Use relative links for supporting files and follow the publication checks below.

## Preview and publish

```bash
npm run start
```

Inspect the preview, then stop the server with Ctrl+C and run:

```bash
npm run typecheck
npm run test:collection
npm run build
npm run test:library-build
npm run serve
```

Open the library at `/collection/` and the generated article to check its content,
images and downloads. The development server watches content changes. Submit the
entry folder in a pull request targeting upstream `main`. After merge, wait for
**Deploy Docusaurus to GitHub Pages** to succeed, then verify the live collection,
article, attachments and source download. Pushing a branch alone
does not publish the website.

When all checks pass, commit the complete entry folder, including images and
linked attachments. Review the staged changes before committing:

```bash
git add library/scenarios/my-range/
git diff --cached
git commit -m "Add my-range library scenario"
git push -u origin add-my-range
```

Open a pull request from your branch into `cradle-lang/cradle-lang.github.io`'s
`main`, complete its PR template, and resolve failing checks. Keep unrelated
release changes and generated files out of the commit. Maintainers review and
merge the contribution. Verify the published entry at
`https://cradle-lang.org/collection/?scenario=my-range` and its article at
`https://cradle-lang.org/library/scenarios/my-range` after the Pages workflow
succeeds. Check the download and all linked assets as well.

## Inspect and adapt

Each entry has a stable link such as `/collection/?scenario=hello-world`.
Open it in Workbench to inspect the topology and event sequence. Loading the
specification requires an explicit click and confirms replacement of an existing
source. Export your changes and commit them before running GitHub automation.

## Validate a committed revision

After the workflow is merged into the default branch, open **Actions → Validate and compile
collection scenario → Run workflow**. Select the scenario and a Git revision.
The workflow installs CradleXC through the project's documented APT repository,
validates and compiles the source internally. Its run summary records the exact
source commit, installed compiler version and static scenario relationships.

This is a compilation check, not an ephemeral range or a deployment. It does not
verify availability of the private dependencies referenced by the initial
examples. The compiler installation follows the current APT package; rerunning
the same Git commit may use a newer compiler. Pin the package and backend
versions in a deployment workflow when exact reconstruction is required.

## What compilation checks

The workflow runs `cxc validate` and `cxc compile` on a GitHub-hosted runner.
Read the validation and compilation results in the completed run’s summary,
along with its source revision, compiler version and static scenario report.
Compiled YAML and source bundles are not uploaded. Download the specification
using the collection page’s top **Download .cradle** button. The **Report** tab
shows the same text summary as Workbench without requiring a workflow run; this
static view does not establish that compiler validation has passed.

Runtime images, remote artifacts and testbed credentials are not supplied by the
library. Compilation does not launch machines, provision services, run event
scripts or prove that runtime dependencies are available. Running a simulation
is a separate activity for a testbed operator with the appropriate dependencies
and access. No automatic scenario deployment workflow is included.
