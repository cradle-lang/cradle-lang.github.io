# Evaluation of Attack-Graph and PDF-Only CTI Question Answering Using Qwen 3.8

**Language model**: Qwen 3.8
**Attack-graph generation algorithm**: MM-Attackg
**Source document**: APT32 threat intelligence report

## 1. Executive Summary

This report evaluates two methods of using **Qwen 3.8** to answer questions about an APT32 cyber threat intelligence report:

1. **Direct PDF analysis**: Model answers using evidence retrieved directly from the report.
2. **Attack-graph-assisted analysis**: Model answers using a structured attack graph generated by MM-Attackg and linked back to the report evidence.

Four questions were selected to test different analytical requirements, including technique verification, infrastructure identification, relationship analysis and end-to-end attack reconstruction.

These questions are:

1. **Was T1059 used? Give the exact supporting evidence.**
2. **What command-and-control infrastructure was associated with the APT32-specific backdoor and how was the communication classified under MITRE ATT&CK?**
3. **How were PowerShell, `mshta.exe` and the scheduled tasks related during the compromise?**
4. **Trace the attack from the victim opening the malicious content to the deployment of the final backdoor.**

The evaluation found that both approaches were able to retrieve key facts from the report. The direct PDF method was generally effective for straightforward questions and exact quotation retrieval. However, its performance declined when the answer required multiple pieces of evidence to be connected across different parts of the report.

The attack-graph-assisted method produced more structured and complete answers, particularly for questions involving relationships and multi-stage attack sequences. It was more effective at connecting scheduled tasks, execution utilities, scripting languages, backdoors and command-and-control infrastructure.

The attack graph did not eliminate the need for source verification. Some technique mappings were not fully supported by the displayed evidence and some verification sections selected edges or sentences that were less relevant than the evidence used in the main answer.

From a business and operational perspective, the attack graph provides a stronger foundation for scalable CTI analysis. The recommended implementation is to use MM-Attackg for structured retrieval and relationship analysis, with the original PDF retained as the authoritative source for final evidence and ATT&CK validation.

## 2. Business Objective

The purpose of this evaluation is to determine which approach provides greater value for analysts and decision-makers when reviewing complex threat intelligence reports.

The assessment focuses on whether each approach can:
* Identify the correct entities and indicators.
* Explain how the entities are related.
* Reconstruct multi-stage attack activity.
* Associate observed behavior with MITRE ATT&CK.
* Provide evidence that can be audited.
* Produce answers suitable for operational and management reporting.

The objective is to determine which evidence representation enables Qwen 3.8 to analyze threat intelligence content more effectively. A more efficient approach could improve analyst throughput, reduce report-review backlogs, and support the timely assessment of a greater volume of threat intelligence while maintaining source-level verification.


## 3. Evaluation Method
The same language model, Qwen 3.8, was used for both approaches. The main difference was the form in which evidence was presented to the model.

| Component | Direct PDF method | Attack-graph method |
|---|---|---|
| Language model | Qwen 3.8 | Qwen 3.8 |
| Primary evidence | Retrieved report passages | MM-Attackg graph facts |
| Data structure | Unstructured text | Entities, edges and relations |
| Relationship extraction | Performed during answer generation | Represented explicitly in the graph |
| Multi-hop analysis | Requires combining multiple passages | Uses connected graph paths |
| Visual evidence | Limited | Can be represented as graph facts |
| Final authority | Original report | Original report |

Using the same language model makes the comparison more focused. Differences in answer quality are more likely to result from evidence representation and retrieval rather than differences between models. 

For a fully controlled experiment, both approaches should also use the same generation parameters, retrieval limits, prompts and ATT&CK reference material.

> “Once macros were enabled on the target system, the malicious macros created two named scheduled tasks as persistence mechanisms for two backdoors on the infected system.”

> “The first named scheduled task launched an application whitelisting script protection bypass to execute a COM scriptlet that dynamically downloaded the first backdoor from APT32’s infrastructure and injected it into memory. ## 7. Analysis of Question 1: T1059 Verification

### Direct PDF result

In a PDF, it did not confirm T1059 because the report did not explicitly state the technique identifier. However, it identified direct behavioral evidence:
> “The second named scheduled task … ran a JavaScript code block that downloaded and launched a secondary backdoor, delivered as a multi-stage PowerShell script.”

This evidence supports:
* **T1059.001 – PowerShell**
* **T1059.007 – JavaScript**

MITRE defines T1059.001 as the abuse of PowerShell commands and scripts for code or payload execution:
> Adversaries may abuse PowerShell commands and scripts for execution. PowerShell is a powerful interactive command-line interface and scripting environment included in the Windows operating system.

The direct PDF answer was therefore cautious, but its requirement for the exact identifier to appear in the report was more restrictive than standard behavioral ATT&CK mapping.

### Attack graph result

The graph response confirmed T1059 and identified numerous related graph edges and source sentences. This produced a more operationally useful analytical conclusion because ATT&CK techniques are typically inferred from observed behavior.

However, the final verification output displayed generic statements about APT32 using malware. These statements did not directly demonstrate PowerShell or JavaScript execution.

### Business assessment

The graph enabled stronger behavioral recognition, but the final formatter should have selected the PowerShell and JavaScript evidence instead of generic malware-use edges.

| Measure | Direct PDF | Attack graph |
|---|---|---|
| Technique recognition | Overly conservative | Correctly inferred |
| Exact behavioral evidence | Located | Available but not prioritized |
| Operational usefulness | Moderate | Higher |
| Validation requirement | Source review | Evidence-ranking improvement |

## 8. Analysis of Question 2: C2 Infrastructure and ATT&CK Classification

Both methods correctly identified:
- `blog.panggin[.]org`
- `share.codehao[.]net`
- `yii.yiihao126[.]net`

Sentence 126 directly states that the APT32-specific backdoor was:
> "configured to communicate with" these domains

### Direct PDF result

The PDF answer classified the communication as:
* **T1071.001 – Application Layer Protocol: Web Protocols**

**T1071.001 – Application Layer Protocol: Web Protocols** is defined as:
```text
Adversaries may communicate using application layer protocols associated with web traffic to avoid detection/network filtering by blending in with existing traffic.
```

This classification is plausible, but the report evidence does not specify HTTP, HTTPS, WebSocket or another web protocol. Communication with a domain name does not automatically establish the use of a web protocol.

### Attack graph result

The graph classified each relationship as:
* **T1568 – Dynamic Resolution**

**T1568 – Dynamic Resolution** is defined as:
```text
Adversaries may dynamically establish connections to command and control infrastructure to evade common detections and remediations.
```

The graph provided specific edges for each backdoor-to-domain relationship:
| Edge | Subject | Relation | Object | Evidence |
|---|---|---|---|---|
| `edge_094` | APT32-specific backdoor shellcode | Configured to communicate with | `blog.panggin[.]org` | Text, Sentence 126 |
| `edge_095` | APT32-specific backdoor shellcode | Configured to communicate with | `share.codehao[.]net` | Text, Sentence 126 |
| `edge_096` | APT32-specific backdoor shellcode | Configured to communicate with | `yii.yiihao126[.]net` | Text, Sentence 126 |
| `edge_202` | APT32-specific backdoor shellcode | Communicates with | `blog.panggin.org` | Visual evidence |
| `edge_203` | APT32-specific backdoor shellcode | Communicates with | `share.codehao.net` | Visual evidence |
| `edge_204` | APT32-specific backdoor shellcode | Communicates with | `yii.yiihao126.net` | Visual evidence |

This provided a clearer representation of the infrastructure relationships. However, the source evidence did not describe dynamic DNS, domain generation, fast flux, or DNS calculation. The T1568 classification should therefore be treated as graph-derived rather than fully verified.

### Business assessment

The direct PDF and graph methods both retrieved the correct indicators. The graph offered a more useful representation because each domain was connected to the backdoor through an explicit relation.

The technique disagreement demonstrates that ATT&CK mapping should be independently validated, regardless of the retrieval method.

| Measure | Direct PDF | Attack graph |
|---|---|---|
| Domain accuracy | Correct | Correct |
| Relationship clarity | Correct narrative | Explicit individual edges |
| Technique | T1071.001 | T1568 |
| Technique verification | Inconclusive | Inconclusive |
| Infrastructure analysis | Adequate | More structured |


## 9. Analysis of Question 3: Scheduled Tasks, mshta.exe and PowerShell

The source evidence supports the following relationship:

```text
ScheduledDefrags
    → ran mshta.exe every 50 minutes
    → initiated JavaScript execution
    → downloaded or invoked PowerShell
    → deployed APT32 backdoor shellcode
```

### Direct PDF result

The PDF answer correctly stated that ScheduledDefrags repeatedly ran `mshta.exe` and that the resulting execution chain deployed a PowerShell-based payload.

The answer remained close to the source but simplified the chain by omitting JavaScript from its summary.

### Attack graph result

The graph provided individual relationships:

- ScheduledDefrags runs mshta.exe.
- ScheduledDefrags executes mshta.exe.
- The PowerShell script delivers the secondary backdoor.
- mshta.exe launches the APT32 backdoor shellcode.

These graph edges make it easier to inspect how individual components contributed to the compromise.

The relevant ATT&CK behaviours are:

| Behaviour | MITRE ATT&CK technique | Exact MITRE definition |
|---|---|---|
| Recurring execution through a scheduled task | **T1053.005 – Scheduled Task/Job: Scheduled Task** | “Adversaries may abuse the Windows Task Scheduler to perform task scheduling for initial or recurring execution of malicious code.” |
| Abuse of `mshta.exe` | **T1218.005 – System Binary Proxy Execution: Mshta** | “Adversaries may abuse mshta.exe to proxy execution of malicious .hta files and Javascript or VBScript through a trusted Windows utility.” |
| JavaScript execution | **T1059.007 – Command and Scripting Interpreter: JavaScript** | “Adversaries may abuse various implementations of JavaScript for execution.” |
| PowerShell execution | **T1059.001 – Command and Scripting Interpreter: PowerShell** | “Adversaries may abuse PowerShell commands and scripts for execution.” |

### Business assessment

The graph response was more useful for relationship analysis because it represented each connection separately. This structure supports auditing, visualization and further investigation.

Its limitation was that the direct `mshta.exe`-to-PowerShell transition was reconstructed from several edges and source sentences rather than represented by a single explicit edge.

## 10. Analysis of Question 4: End-to-End Attack Reconstruction

### Direct PDF result

The PDF response identified:

* The malicious ActiveMime file
* The fake error messages
* Macro enablement
* Payload download
* Scheduled-task creation

However, it stopped after the scheduled tasks were created. It did not explain how either task resulted in backdoor deployment.

The answer therefore did not reach the endpoint requested in the question.

### Attack graph result 

The graph reconstructed both attack branches.

#### First branch

```text
First scheduled task
    → application-whitelisting bypass
    → COM scriptlet
    → download from APT32 infrastructure
    → first backdoor injected into memory
```

#### Second branch

```text
ScheduledDefrags
    → mshta.exe
    → JavaScript
    → multi-stage PowerShell
    → APT32-specific backdoor shellcode
```

This was the most significant performance difference in the evaluation. MM-Attackg enabled Qwen 3.8 to retrieve and combine relationships across several report sentences into a coherent attack sequence.

### Business assessment

The attack graph demonstrated a clear relative advantage. Its ability to preserve branches and connect events across the report made the final answer more complete and operationally relevant.

The verification block should nevertheless have displayed the sentences and edges covering macros, scheduled tasks, script execution and backdoor deployment instead of campaign-targeting evidence.

## 12. Why the Attack Graph Is the More Suitable Approach

### Structured knowledge representation

MM-Attackg converts unstructured report content into structured entities and relationships. This reduces the need for Qwen 3.8 to reconstruct every connection during response generation, as the relevant relationships are already represented through graph edges.

For example:
```text
ScheduledDefrags — runs → mshta.exe
PowerShell script — delivers → secondary backdoor
Backdoor — configured to communicate with → C2 domain
```

This structure is easier to review, search, visualize and reuse

### More effective multi-hop analysis

Threat intelligence questions often require information from multiple paragraphs, tables and figures. The graph enables Qwen 3.8 to follow connected paths across the report rather than relying solely on semantic similarity between the question and individual passages.

This was most evident in the full attack-chain question, where the graph reached backdoor deployment while the PDF-only response stopped at scheduled-task creation.

### Clearer separation of parallel attack branches

The report describes two scheduled tasks supporting two separate backdoor deployment paths. The attack graph preserved this branching structure more effectively, reducing the risk of combining distinct execution mechanisms into a single linear sequence.

### Greater potential for auditability

Graph identifiers can support an auditable evidence path:

```text
Final claim
    → graph edge
    → source sentence or figure
    → original report
```

This is valuable for management review, analyst validation and regulated reporting.

### Reusability and scalability

Once the graph has been generated, the same structured relationships can support:
* Additional investigative questions
* Attack-path visualization
* Indicator correlation
* Technique summaries
* Cross-report comparisons
* Detection engineering
* Analyst briefings

A direct approach may need to repeat retrieval and relationship reconstruction for every new question. 

## 13. Risks and Controls

Graph-derived conclusions should not be treated as authoritative without source-level validation. This evaluation identified several necessary controls.

| Risk | Recommended control |
|---|---|
| Incorrect technique assigned to an edge | Validate against the official ATT&CK definition |
| Weak evidence displayed | Rank evidence by direct relevance to the answer |
| Unrelated verification sentence included | Require entity and relation overlap with the claim |
| Graph path omits an intermediate stage | Preserve complete paths for sequence questions |
| Inference presented as fact | Label claims by verification status |
| Text and visual evidence disagree | Return both sources for analyst review |

Recommended verification labels are:
- Source-confirmed
- Behaviorally supported
- Graph-derived
- Externally corroborated
- Insufficient evidence

## 14. Recommendation
MM-Attackg should be used as the primary evidence-organization and relationship-retrieval layer for Qwen 3.8. The original PDF should remain the authoritative validation source.

The recommended workflow is:

```text
Original report
      ↓
MM-Attackg graph generation
      ↓
Graph-based retrieval and path analysis
      ↓
Qwen 3.8 response generation
      ↓
Source-sentence validation
      ↓
ATT&CK definition validation
      ↓
Final analyst-ready answer
```

This approach takes advantage of the graph’s stronger relationship reasoning without losing the evidentiary reliability of the original report.

## 15. Final Conclusion

The evaluation indicates that Qwen 3.8 benefits from the structured context provided by the MM-Attackg attack graph. Both methods performed effectively for direct factual retrieval. However, the graph-assisted approach demonstrated stronger performance for relationship-based, multi-stage, and attack-path questions.

Its clearest advantage was observed in the end-to-end reconstruction of the compromise, where it connected the malicious attachment, macro execution, scheduled tasks, `mshta.exe`, JavaScript, PowerShell, backdoor shellcode and C2 infrastructure. The direct PDF approach retrieved several of these facts but did not consistently combine them into a complete sequence.

The findings support using the attack graph as the primary evidence-organization and relationship-retrieval layer for complex CTI analysis. Graph-derived answers should nevertheless be validated against the original report, particularly when they contain inferred relationships or MITRE ATT&CK classifications.

> *Business recommendation*: Adopt a graph-assisted, source-verified workflow in which MM-Attackg supports evidence organization and multi-hop reasoning, Qwen 3.8 generates the analytical response, and the original report remains the authoritative source for final evidence and ATT&CK validation
