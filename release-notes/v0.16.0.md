# Announcing CradleXC 0.16.0

<!-- markdownlint-disable-next-line MD036 -->
*26 August 2026*

CradleXC 0.16.0 is a command-line toolchain for defining, validating and
processing reproducible cyber-range scenarios written in CRADLE.

This release is useful to scenario authors who need a clear separation between
source validation, compiler output and target-specific generation, and to
operators who need to run a selected deployment backend or extract forensic
data from a deployment.

The release also makes backend integration explicit: `cxc` discovers external
`cxc-backend-<name>` executables instead of compiling a deployment backend into
the core CLI.

## Highlights

* Validate CRADLE source and compile it to YAML.
* Inspect AST, HIR and Deployment IR representations.
* Generate target-specific files through external backend plugins.
* Run staged deployment workflows and destroy deployments through a selected backend.
* Import supported Vagrant/Ansible layouts and generate C or PowerShell artifacts.
* Check the local environment with `cxc doctor`.

## Added

### External backend plugins

CradleXC discovers deployment backends as executables named
`cxc-backend-<name>`. The CLI keeps backend-specific behavior outside the core
compiler and passes backend options through generic `--backend-arg key=value`
arguments or matching `[backend.<name>]` configuration tables.

List discovered backends with:

```bash
cxc backend list
```

### Compiler inspection and artifact workflows

In addition to validation and YAML compilation, the CLI can expose successive
compiler representations:

```bash
cxc parse -i <scenario.cradle>
cxc check -i <scenario.cradle>
cxc dump-hir -i <scenario.cradle>
cxc dump-ir -i <scenario.cradle>
```

APT scenarios can generate artifacts from a YAML configuration:

```bash
cxc generate-artifacts -i <artifact.yml> -o ./build
```

The `--project` option generates all objects from a project `index.yaml`.

### Import and deployment commands

Supported static Vagrant/Ansible layouts can be imported into validated CRADLE
source:

```bash
cxc import \
  --from /path/to/deployment \
  --name ImportedLab \
  --output scenarios/ImportedLab.cradle
```

Deployment is explicit and backend-dependent. For example, a selected backend
can run all stages or one stage:

```bash
cxc deploy -i <scenario.cradle> --backend <backend>
cxc deploy -i <scenario.cradle> --backend <backend> --stage provision
```

`cxc emit` generates backend files without running deployment stages:

```bash
cxc emit -i <scenario.cradle> --target <backend> -o ./output
```

## Changed

### Backend separation and configuration

The core `cxc` package no longer contains an in-tree deployment backend.
Vagrant, SPHERE and libvirt-Ansible integrations are external plugins and are
discovered in the normal executable search paths. Backend-specific settings
belong under `[backend.<name>]`; command-line backend arguments override values
from that table.

The configuration search order is:

1. an explicit `--config` path;
2. `./config.toml`;
3. `config.toml` beside the executable;
4. `~/.cxc/config.toml`;
5. built-in defaults.

## Fixed

### Dependency reporting

`cxc doctor` reports dependency checks supplied by discovered backend plugins.
It no longer treats the Rust toolchain as a runtime requirement for a
prebuilt CradleXC package. Missing required dependencies are listed and the
command provides the `cxc install-deps` guidance.

## Installation and upgrade

Build the CLI from this source checkout with:

```bash
cargo install --path crates/cradle-cli
```

The release package is installed as the `cxc` command. Verify the installation
and inspect the environment with:

```bash
cxc --version
cxc doctor
```

Backend plugins are installed and upgraded independently from the core CLI.
Use the plugin's release documentation for its compatibility requirements.

## Known limitations

`cxc emit` generates files but does not execute them. `cxc deploy` can provision
or run events only when the selected external backend and its provider
dependencies support those stages. Import is intentionally conservative:
dynamic Ruby, Ansible includes, roles and arbitrary module behavior cannot be
decompiled reliably.
